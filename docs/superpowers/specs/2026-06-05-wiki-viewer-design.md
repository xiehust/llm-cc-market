# Wiki Viewer Design

## Goal

Build a local live website for browsing the knowledge generated by
`cc-knowledge` and `llm-wiki`. The site should read the user's wiki hub at
runtime, let users navigate topics and markdown files, search across the wiki,
and read articles in a pixel-art Library Shelf interface.

## Scope

The first version is a local developer tool, not a hosted publishing system. It
will run from this repository and read the wiki hub from the local filesystem.
It will support the llm-wiki hub layout described by this repo:

- Hub registry: `wikis.json`
- Topic content: `topics/<topic>/raw/**`, `topics/<topic>/wiki/**`,
  `topics/<topic>/inventory/**`, `topics/<topic>/output/**`
- cc-knowledge lessons: `topics/<topic>/raw/notes/YYYY-MM-DD-ll-*.md`
- Pending proposals: `topics/<topic>/.librarian/proposals/*.proposal.md`

Static export, hosted auth, editing wiki files in the browser, and LLM-backed
query synthesis are out of scope for the first version.

## Product Behavior

The homepage presents active topic wikis as pixel-art shelves. Each topic shows
counts for raw notes, compiled wiki articles, proposals, and recent updates.

Users can:

- Browse active topics from the shelf homepage.
- Open a topic and browse grouped sections such as raw notes, concepts, topics,
  references, proposals, inventory, and output.
- Search across all indexed files or within a selected topic.
- Open a markdown file in a reader view with rendered markdown, frontmatter
  metadata, tags, source links, and a visible file path.
- Toggle archived topics on when needed; archived topics are hidden by default.
- See setup and warning states when the wiki hub is missing, unreadable, or has
  malformed files.

The interface uses the approved Library Shelf direction: playful pixel-art
visuals, blocky borders, shelf/book metaphors, compact metadata badges, and
restrained colors. The reader remains practical and readable rather than
decorative.

## Architecture

Add a new app at `apps/wiki-viewer`.

The app has two parts:

1. A small Node HTTP API that reads the filesystem.
2. A Vite React frontend that renders the pixel-art wiki UI.

The local dev command starts both pieces together. The frontend never reads the
filesystem directly; it calls the API.

### Hub Resolution

The API resolves the hub path in this order:

1. `WIKI_HUB_PATH` environment variable, if set.
2. `~/.config/llm-wiki/config.json` `hub_path`, expanding only a leading `~`.
3. `~/wiki`.

Older `resolved_path` values are not used as the primary source of truth. If a
configured hub path exists but cannot be read, the API reports the permission or
I/O problem instead of silently falling back to a different path.

### Indexing

On request, the API scans the hub and returns an in-memory index of markdown
documents. It reads `wikis.json` when available and also tolerates topic
directories that exist under `topics/`.

Each indexed document contains:

- Stable id
- Topic slug and path
- Relative file path
- Section kind: raw, wiki, proposal, inventory, output, config, log, or index
- Article category where available: concept, topic, reference, thesis, notes
- Title, summary, tags, dates, confidence, source fields from frontmatter
- Body text for rendering and search
- Archived status inherited from registry status or `topics/.archive/`

Malformed frontmatter is recorded as a warning and the file can still appear
with best-effort metadata. Unreadable files are skipped and surfaced through the
status endpoint.

### API Endpoints

The expected API surface is:

- `GET /api/status`: hub path, counts, warnings, and setup state.
- `GET /api/topics?includeArchived=false`: topic list with counts and metadata.
- `GET /api/topics/:topic`: topic detail and grouped documents.
- `GET /api/documents/:id`: document metadata and markdown body.
- `GET /api/search?q=...&topic=...&includeArchived=false`: keyword search.

The document id must be derived from path data, not array position, so links
remain stable across rescans.

### Search

Search is local keyword matching over title, summary, tags, relative path, and
body text. Results are ranked by simple field weight:

1. Title
2. Tags and summary
3. File path
4. Body content

The first version does not require a separate search index dependency. The index
can be rebuilt on each API request or cached with filesystem timestamps if the
implementation stays simple.

## Frontend Design

The UI has these primary views:

- Shelf home: topic shelves, global search, active/archived toggle, status
  warnings.
- Topic view: topic header, counts, grouped file shelves, recent files.
- Search results: query input, filters, result snippets, badges.
- Reader view: markdown content, metadata drawer/sidebar, related file links
  from the same topic and tags.
- Setup view: missing hub guidance with resolved path and expected commands.

Pixel-art design rules:

- Use square/blocky borders, crisp shadows, and book/shelf visual cues.
- Keep cards to individual topic/file items only.
- Keep colors varied and readable, avoiding one-hue dominance.
- Make the reader typography stable and comfortable for long markdown files.
- Ensure mobile screens collapse to a single-column layout with no text overlap.

## Error Handling

The app should handle:

- Missing hub: show setup view and checked paths.
- Missing or invalid `wikis.json`: continue from `topics/` if possible and show
  a warning.
- Permission errors: show the exact failed path and error message.
- Malformed frontmatter: show a non-blocking warning and render file body.
- Empty wiki: show an empty shelf state.

## Testing

Use test-driven development for the implementation.

Focused tests should cover:

- Hub path resolution order.
- Registry parsing and active versus archived topic detection.
- Markdown/frontmatter parsing for raw notes and compiled wiki articles.
- Index grouping and counts.
- Search ranking and topic filtering.
- API responses against a temporary fixture wiki.

Frontend verification should include running the dev server and checking the site
in desktop and mobile viewport sizes. The page must show the shelf UI, working
search, a topic view, and a rendered markdown document.

## Open Decisions

The approved decisions are:

- Viewer type: local live viewer.
- Visual direction: pixel-art Library Shelf.
- First-version scope: browse, search, and read only.

No unresolved product decisions remain for the first implementation plan.
